# 오늘 저녁 뭐 먹지 (DinnerDecision) — 개발 계획서

> 버전 0.1 · 작성일 2026-11-09 · 상태: 초안 (검토 요청)

---

## 1. 개요

### 1.1 목적
현재 위치 기준 1km 안의 음식점을 네이버 지도로 찾아 메뉴(한식·중식·일식·양식)별로 보여주고,
**날씨**와 **최근에 간 식당·메뉴 기록**을 함께 보고 "오늘의 추천 식당·메뉴"를 **추천 이유와 함께** 제시하는 모바일 앱.

### 1.2 해결하려는 문제
- 매일 "뭐 먹지?" 고민 → 결정 시간 단축
- 늘 가던 곳만 가게 됨 → 최근 기록을 피해 **다양하게** 추천
- 날씨를 고려하지 않은 선택 → 비·추위·더위에 맞는 메뉴 추천

### 1.3 지원 플랫폼
- Android 8.0 (API 26) 이상
- iOS 15 이상

## 2. 유사 앱 분석 및 차별점

| 앱 | 참고할 점 | 부족한 점 |
|---|---|---|
| PickOne | 위치 기반 주변 식당, 거리·영업 중 필터, 방문 기록(별점·메모·사진) | 날씨 반영 없음, 기록이 추천에 반영되지 않음 |
| 뭐먹지? | 네이버 지도·카카오맵 연동, 제철 음식 추천 | 실시간 날씨가 아닌 계절 기준 |
| Selunch | 룰렛 UI, 추천 히스토리, 메뉴 목록 직접 편집 | 위치 기반 아님 |
| 랜덤맛집 / 흥돌아 어디가까? | 원하지 않는 식당 제외 기능 | 직접 일일이 제외해야 함, 지역 제한 |
| 오뭐먹? | 카드를 넘기는 게임형 UI | 기록·날씨 없음 |
| VibeEats (해외) | AI가 날씨·기분 반영, 비 오는 날 실내 추천 | 국내 식당 데이터 없음 |

**우리 앱의 차별점**
1. **날씨 + 방문 기록 + 주변 식당**을 한 번에 반영하는 국내 앱은 찾지 못함
2. 최근 먹은 메뉴·식당을 **자동으로** 피함 (직접 제외할 필요 없음)
3. **추천 이유를 문장으로 설명** ("비가 와서 국물 요리 / 한식은 3일 연속이라 제외 / 450m 거리")
4. **달력**으로 식사 기록을 쌓아 두고 다시 볼 수 있음

## 3. 요구사항

### 3.1 기능 요구사항

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-01 | 현재 위치 | GPS로 현재 좌표 확인, 권한 요청, 위치를 직접 설정할 수도 있음 | 필수 |
| F-02 | 주변 음식점 목록 | 네이버 검색으로 반경 **1km 안** 음식점 목록 (거리순) | 필수 |
| F-03 | 메뉴 분류 | **한식 / 중식 / 일식 / 양식** 탭 또는 칩으로 필터 (+ 전체) | 필수 |
| F-04 | 식당 상세 | 식당 이름을 누르면 상세 화면: 주소, 전화, 카테고리, 거리, 지도, 방문 기록 | 필수 |
| F-05 | 네이버 지도 연결 | 상세 화면에서 네이버 지도 앱(없으면 웹)으로 열기·길찾기 | 필수 |
| F-06 | 지도 보기 | 목록 ↔ 지도 전환, 식당 마커 표시 | 필수 |
| F-07 | 식사 기록 입력 | 날짜, 식당, 메뉴, 분류, 별점, 메모, 사진(선택) 저장 | 필수 |
| F-08 | 기록 달력 | 월간 달력에 간 날 표시, 날짜를 누르면 그날 기록 보기·수정·삭제 | 필수 |
| F-09 | 오늘의 추천 | 버튼을 누르면 날씨와 기록을 반영해 식당·메뉴 1~3개 추천 + **추천 이유** | 필수 |
| F-10 | 다시 추천 | 마음에 안 들면 "다른 추천" (이번에 거절한 식당은 제외) | 필수 |
| F-11 | 추천 → 기록 | "여기로 결정" → 바로 오늘 기록으로 저장 | 권장 |
| F-12 | 통계 | 이번 달 분류별 비율, 자주 간 식당 TOP 5 | 선택 |
| F-13 | 제외 목록 | 안 갈 식당 숨기기, 못 먹는 음식 설정 | 선택 |
| F-14 | 백업·복원 | 기록을 파일로 내보내기·가져오기 (기기 변경 대비) | 권장 |

### 3.2 비기능 요구사항
- **성능:** 주변 목록 3초 안에 표시, 같은 위치는 캐시로 다시 검색하지 않음 (10분)
- **오프라인:** 기록과 달력은 인터넷 없이 사용 가능 (로컬 DB)
- **개인정보:** 위치·기록은 기기 안에만 저장. 서버는 위치를 저장하지 않음
- **보안:** API 비밀키(Client Secret)를 앱에 넣지 않음 → 중계 서버 사용 (6장)
- **법·약관:** 위치정보법 확인 (위치를 서버에 저장하지 않으면 사업자 신고 부담이 줄어듦, 출시 전 확인), 네이버 API 이용약관과 출처 표시 준수

## 4. 핵심 기술 이슈 (중요)

### 4.1 네이버 검색 API의 제약
`https://openapi.naver.com/v1/search/local.json` (지역 검색)

| 항목 | 내용 |
|---|---|
| 한 번에 받을 수 있는 결과 | **최대 5개** (`display` 최대 5) |
| 좌표·반경 검색 | **지원하지 않음** (키워드 검색만 됨) |
| 응답 좌표 | `mapx`, `mapy` (WGS84 경위도 × 10⁷) |
| 하루 호출 한도 | 25,000회 |

→ "내 위치 1km 안 음식점 전부"를 한 번에 받을 수 없음.

### 4.2 대응 방안: 다중 키워드 검색 + 거리 필터
1. 현재 좌표 → **역지오코딩**(Naver Cloud Reverse Geocoding)으로 동 이름 확인 (예: `성수동2가`)
2. 분류별 세부 키워드로 여러 번 검색

   | 분류 | 검색 키워드 예 |
   |---|---|
   | 한식 | 한식, 국밥, 찌개, 고기집, 냉면, 분식 |
   | 중식 | 중식, 중국집, 짬뽕, 마라탕, 양꼬치 |
   | 일식 | 일식, 초밥, 라멘, 돈까스, 이자카야 |
   | 양식 | 양식, 파스타, 피자, 스테이크, 햄버거 |

   → `"{동이름} {키워드}"` 조합, 인접 동까지 포함 (`sort=comment` / `random` 둘 다 사용)
3. 결과를 합쳐 **중복 제거** (이름 + 주소 기준)
4. `mapx/mapy`로 현재 위치와의 거리(하버사인 공식) 계산 → **1km 넘는 곳 제외**
5. 응답의 `category` (예: `한식>국밥`)로 4개 분류에 맞춤
6. 결과를 서버와 기기에 캐시해서 호출 수를 줄임

> 한계: 검색 키워드에 안 걸리는 식당은 빠질 수 있음. 1차 버전은 이렇게 하고 정확도를 측정함.

### 4.3 대안 (결정 필요)
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 네이버만** | 위 4.2 방식 | 요구사항 그대로, 네이버 데이터 | 누락 가능, 호출 수 많음 |
| **B. 혼합 (권장)** | 목록은 **카카오 로컬 카테고리 검색**(음식점 `FD6`, 좌표+반경 1000m 지원), 지도 표시·상세 연결은 **네이버 지도** | 1km 반경 검색이 정확 | API 두 개 관리, 데이터 출처가 섞임 |
| C. 카카오만 | 카카오맵 SDK + 로컬 API | 구현 가장 간단 | "네이버 지도" 요구사항과 다름 |

→ **1차 버전은 A로 개발하되, 검색 모듈을 인터페이스로 분리**해서 B로 바꿀 수 있게 설계.

## 5. 기술 스택

### 5.1 앱 프레임워크 비교

| 항목 | **Flutter (권장)** | .NET MAUI | React Native |
|---|---|---|---|
| 언어 | Dart | **C# (현재 쓰시는 언어)** | TypeScript |
| 네이버 지도 SDK | `flutter_naver_map` (비공식이지만 꾸준히 관리, Naver Map SDK 3.22 반영, 2026년 4월 업데이트) | 관리되는 바인딩 없음 → WebView + JS API로 대체 | 커뮤니티 패키지 있음 |
| 달력 UI | `table_calendar` | 직접 구현 또는 유료 컴포넌트 | 패키지 있음 |
| Android·iOS 동시 지원 | 좋음 | 좋음 | 좋음 |
| 학습 부담 | 중간 (Dart는 C#과 비슷함) | 낮음 | 중간 |

**권장: Flutter.** 네이버 지도 네이티브 SDK를 바로 쓸 수 있는 점이 가장 큼.
Dart 문법이 C#과 많이 비슷해서(클래스, async/await, 제네릭, null 안전성) 적응이 빠름.
> C#을 꼭 써야 하면 .NET MAUI + WebView 네이버 지도로도 가능하지만 지도 성능과 연동 작업량이 불리함.

### 5.2 구성 요소

| 구분 | 기술 |

## 6. 시스템 구조

```
┌──────────────── 모바일 앱 (Flutter) ────────────────┐
│  UI (화면)                                           │
│   ├ 홈/목록  ├ 지도  ├ 식당 상세  ├ 추천  ├ 달력     │
│  ─────────────────────────────────────────────────  │
│  서비스                                              │
│   ├ LocationService   (GPS)                          │
│   ├ PlaceRepository   (검색·거리 필터·분류·캐시)      │
│   │    └ IPlaceSource ← NaverPlaceSource / KakaoPlaceSource │
│   ├ WeatherService    (날씨)                          │
│   ├ RecommendEngine   (점수 계산 + 이유 생성)          │
│   └ MealLogRepository (기록 CRUD)                     │
│  ─────────────────────────────────────────────────  │
│  로컬 DB (SQLite): 식사 기록, 식당 캐시, 설정          │
└───────────────────────┬─────────────────────────────┘
                        │ HTTPS (앱 전용 키)
┌───────────────────────▼─────────────────────────────┐
│ 중계 서버 (Cloudflare Workers / Firebase Functions)   │
│  - API 비밀키 보관, 호출 횟수 제한, 결과 캐시          │
│  - 위치·개인 기록은 저장하지 않음                      │
└──────┬───────────────┬──────────────────┬───────────┘
       ▼               ▼                  ▼
  네이버 검색 API   Naver Cloud Maps    기상청 단기예보
  (지역 검색)       (역지오코딩)         (공공데이터포털)
```

**중계 서버가 필요한 이유:** 네이버 검색 API의 Client Secret을 앱에 넣으면 앱 파일을 풀어서 키를 빼낼 수 있음.
(지도 SDK의 Client ID는 앱에 넣는 구조라 괜찮음.)

```text

 ├ memo          TEXT
 ├ photo_path    TEXT
```

## 8. 추천 알고리즘

### 8.1 흐름
1. 현재 위치 1km 안의 후보 식당 목록 (제외한 식당 빼기)
2. 현재 날씨 조회 (기온, 강수 형태, 하늘 상태)
3. 최근 기록 조회 (기본 14일)
4. 후보마다 **점수 계산** → 상위 10개 중 **가중 랜덤**으로 1~3개 선택 (매번 같은 결과가 나오지 않게)
5. 점수에 영향을 준 요인을 **추천 이유 문장**으로 변환

### 8.2 점수 (합계 100점 기준, 수치는 테스트하며 조정)

| 요인 | 배점 | 규칙 |
|---|---|---|
| 다양성 — 식당 | 0~30 | 최근 7일 안에 간 식당 **제외**, 8~14일은 감점, 처음 가는 곳은 가산점 |
| 다양성 — 분류 | 0~20 | 최근 3번 중 같은 분류(예: 한식)가 많을수록 감점 |
| 다양성 — 메뉴 | 0~10 | 어제·그제 먹은 메뉴 키워드(예: 국밥)와 같으면 감점 |
| 날씨 적합도 | 0~25 | 아래 날씨 규칙표 |
| 거리 | 0~10 | 가까울수록 가산점 (비·눈 오면 거리 배점 2배) |
| 만족도 | 0~5 | 예전에 별점 4점 이상 준 식당은 (기간이 지났으면) 가산점 |

### 8.3 날씨 규칙 (예)

| 날씨 조건 | 점수 오르는 메뉴·식당 | 이유 문장 예 |
|---|---|---|
| 비·눈 | 국밥, 찌개, 칼국수, 짬뽕, 라멘, 전 / 가까운 곳 | "비가 와서 따뜻한 국물 요리와 가까운 곳을 골랐어요" |
| 기온 5℃ 이하 | 탕, 전골, 샤브샤브, 마라탕 | "기온이 2℃로 추워서 뜨끈한 전골을 추천해요" |
| 기온 28℃ 이상 | 냉면, 소바, 초밥, 물회, 샐러드 | "31℃ 더운 날이라 시원한 냉면을 추천해요" |
| 맑고 선선함 (15~25℃) | 조금 먼 곳·새로운 곳 가산점 | "날씨가 좋아서 조금 걸어도 괜찮은 새 맛집이에요" |
| 흐림·미세먼지 나쁨 | 실내·가까운 곳 | "미세먼지가 나빠서 가까운 곳으로 골랐어요" |

### 8.4 추천 결과 화면 예시
```
🍜 오늘의 추천: 성수 할매순대국 (한식 · 순대국) · 420m

왜 추천하나요?
 ☔ 비가 오고 기온이 9℃라 따뜻한 국물 요리가 좋아요
 🔄 최근 3번이 일식·양식·양식이라 한식으로 바꿨어요
 🆕 아직 가 보지 않은 식당이에요
 📍 걸어서 6분 거리예요

[네이버 지도에서 보기]  [여기로 결정 ✔]  [다른 추천 ↻]
```

## 9. 화면 구성

| 화면 | 주요 요소 |
|---|---|
| **① 홈 (주변 식당)** | 상단: 현재 위치(동 이름)·날씨 요약 / 분류 칩: 전체·한식·중식·일식·양식 / 식당 목록(이름, 세부 분류, 거리, 최근 방문 표시) / 목록↔지도 전환 / 하단 큰 버튼 **[오늘의 추천]** |
| **② 지도** | 네이버 지도, 내 위치, 1km 원, 분류별 색상 마커, 마커를 누르면 미리보기 카드 |
| **③ 식당 상세** | 이름, 분류, 주소, 전화(누르면 전화 걸기), 거리, 작은 지도, [네이버 지도로 열기]·[길찾기], 이 식당 방문 기록, **[기록하기]** |
| **④ 오늘의 추천** | 추천 카드 1~3개 + 추천 이유 목록 + [결정]·[다른 추천] |
| **⑤ 기록 입력** | 날짜(기본 오늘), 식당(검색 또는 직접 입력), 분류, 메뉴, 별점, 메모, 사진 |
| **⑥ 달력** | 월간 달력, 기록 있는 날에 분류 색상 점, 날짜를 누르면 그날 기록 목록, 월 요약(한식 40% 등) |
| **⑦ 설정** | 검색 반경, 피할 기간(일), 못 먹는 음식, 제외 식당 관리, 백업·복원, 권한, 오픈소스·데이터 출처 |

하단 탭: **주변 · 추천 · 달력 · 설정**

## 11. 위험 요소와 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 네이버 검색 API가 5개씩만 돌려주고 반경 검색이 안 됨 | 주변 식당 누락 | 다중 키워드 + 거리 필터, 캐시. 정확도가 부족하면 카카오 카테고리 검색 혼합(4.3의 B안) |
| 하루 호출 한도(25,000회) | 사용자가 늘면 부족 | 서버 캐시(동 단위, 수 시간), 사용자별 호출 제한 |
| `flutter_naver_map`이 비공식 패키지 | 업데이트 지연 가능 | 버전 고정, 지도 부분을 분리해 두기 |
| 날씨 API 장애 | 추천 품질 저하 | 날씨 없이 다양성·거리만으로 추천하고 "날씨 정보 없음" 표시 |
| 위치정보·개인정보 규정 | 스토어 심사·법적 문제 | 위치를 서버에 저장하지 않음, 개인정보처리방침 작성, 권한 사용 이유 문구 |
| iOS 빌드에 Mac 필요 | iOS 빌드 불가 | Mac 장비 확보 또는 Codemagic 등 클라우드 빌드 사용 |
| 앱스토어 정책 (지도 데이터 출처 표시) | 심사 거절 | 네이버 로고·출처 표시, 약관 확인 |

## 13. 결정이 필요한 사항
1. **식당 검색 방식:** A(네이버만) / **B(목록은 카카오, 지도는 네이버, 권장)** / C(카카오만)
2. **앱 프레임워크:** **Flutter (권장)** / .NET MAUI (C#)
3. **중계 서버:** Cloudflare Workers / Firebase Functions / 기존 사내 서버
4. **기록 보관:** 기기에만 저장(1차 권장) / 로그인해서 클라우드 동기화
5. **iOS 빌드 환경:** Mac 보유 여부
